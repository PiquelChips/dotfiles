# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a
skill generated by `create-verification-skill`, or any project-local
verification skill with a feature map. The unit of rigor is the feature, not
every sentence: cover every feature file from source and exercise every
feature live.

## Outcomes

Pick one, and say which:

- **clean:** every feature got source and live coverage, and nothing is worth
  shipping. No branch, no PR.
- **changed:** one PR ships proven doc, harness or map corrections.
- **blocked:** coverage could not finish, or a proven fix could not ship
  safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own directory: its `SKILL.md`,
`features/`, and any scripts it owns. Never edit product code during a run.
A behavior the map describes that the app no longer has is either doc drift
(fix the map) or a product regression (report it, don't paper over it in
docs).

## Pass

0. **Locate the target:** the project-local skill with launch and drive
   sections and a feature map, usually `.agents/skills/verify-*/`. Several
   candidates: ask which one. None: stop and point at
   `create-verification-skill` instead of inventing a target.
1. **Index hygiene.** Read the feature map's README and list its sibling
   files. Fix missing, extra, duplicate or dead entries.
2. **Source wave.** One read-only subagent per feature file, in parallel: a
   native subagent or `delegate_task`. Each explains how its feature works
   from source, flags likely doc drift with citations, and returns one live
   verification recipe. Subagents never drive the app and never edit files.
   Return shape: feature summary, source entry points, likely drift or none,
   one recipe.
3. **Reconcile.** Every feature file has a returned summary. Merge
   overlapping recipes into as few app states as practical. Spot-check cited
   drift; don't re-prove clean claims. Sweep recent churn for user-facing
   surfaces missing from the map, and require a concrete source path before
   calling one missing.
4. **Live pass.** Required even when source looks clean. You own all driving,
   and follow the skill's own launch model: one long-lived instance driven
   serially for servers and UIs, or a fresh isolated session per drive for
   short-lived CLIs. Exercise every feature at least once, and hold three
   invariants whatever fails:
   - Never drive an instance you haven't health-checked since it last did
     something surprising. Run doctor before the first drive, on each fresh
     session, and after any failed drive. Where doctor can't see the failure
     (a wedged UI on a healthy process), reset to a known state or relaunch.
   - Evidence captured so far survives every cleanup, checked at its named
     location, not assumed.
   - Nothing a drive started outlives its usefulness. Clean failed-iteration
     residue whether the session is stuck, exited or shared; for a shared
     instance, clean the residue, not the instance. Never kill by process
     name; kill what you started.

   A doctor failure caused by skill drift is drift: fix it under edit scope
   and retry once, restarting only what the fix invalidated, before calling
   the pass blocked. A feature is unreachable only with the concrete
   prerequisite (auth, entitlement, OS, external state) and the route
   attempted; if the map omits that prerequisite, that's drift. Re-drive
   every harness fix live before it ships. Tear down after the last drive,
   re-proofs included; evidence stays.
5. **Triage.** A wrong or missing user-POV description is doc drift: fix it.
   Working behavior the harness can't drive is a harness gap: fix it, with
   any script executable and its invocation in the skill body. App behavior
   that is actually broken is a product gap: report it to the user and keep
   it out of this PR.
6. **Ship or stop.** For changed: re-read every changed file, then file one
   PR with the `file-pr` skill. For clean or blocked: no PR; report the
   outcome and the coverage honestly.

Keep short run notes (features covered, unreachable prerequisites, confirmed
drift, outcome) in a scratch location. Don't commit them.
